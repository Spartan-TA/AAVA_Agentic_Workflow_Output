### E02: Employee Master Data (CRUD)

#### Title: Create Employee Entity
User Story: As a developer I want to define an Employee entity with fields name, badgeId, role, department, shiftGroup, hireDate, status So that employee data is structured and consistent
Acceptance Criteria:
Scenario: Employee entity defined
Given the codebase is set up
When I inspect the Employee module
Then I should see all required fields with validation
Additional Details:
- Priority: High
- Story Points: 2
- Dependencies: E01
- Notes: badgeId must be unique

#### Title: Employee CRUD APIs
User Story: As an HR user I want to create, read, update, and delete employee records via APIs So that I can manage employee data efficiently
Acceptance Criteria:
Scenario: Create employee
Given I have valid employee data
When I POST to `/employees`
Then a new employee is created and badgeId is unique

Scenario: Update employee
Given an employee exists
When I PUT/PATCH to `/employees/{id}`
Then the employee data is updated

Scenario: Delete employee (soft-delete)
Given an employee exists
When I DELETE `/employees/{id}`
Then the employee is soft-deleted

Scenario: List employees with pagination/filtering
Given employees exist
When I GET `/employees?department=Shipping&page=1`
Then I see filtered, paginated results

Additional Details:
- Priority: High
- Story Points: 5
- Dependencies: E01
- Notes: OpenAPI schemas with examples

#### Title: Employee DTOs for Web/API
User Story: As a frontend developer I want DTOs for employee data So that APIs return consistent, documented responses
Acceptance Criteria:
Scenario: DTOs defined
Given APIs are implemented
When I call `/employees`
Then responses match documented DTOs
Additional Details:
- Priority: High
- Story Points: 2
- Dependencies: Employee CRUD APIs
- Notes: Include examples in OpenAPI
