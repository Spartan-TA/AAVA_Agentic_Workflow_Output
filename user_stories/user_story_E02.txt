## E02: Employee Master Data (CRUD)

### User Story 1: Create Employee Record
**User Story:** As an HR I want to create a new employee record with all required fields So that employee data is centrally managed.

**Acceptance Criteria:**
- Scenario: Valid employee creation
  - Given valid employee data
  - When I POST to `/employees`
  - Then the employee is created and returned with a unique ID

- Scenario: Duplicate badgeId
  - Given an existing badgeId
  - When I POST a new employee with the same badgeId
  - Then the request fails with 409 Conflict

**Priority:** High  
**Story Points:** 5  
**Dependencies:** E01  
**Notes:** badgeId must be unique.

---

### User Story 2: Update Employee Details
**User Story:** As an HR I want to update employee details So that records remain current.

**Acceptance Criteria:**
- Scenario: Update allowed fields
  - Given an existing employee
  - When I PATCH name or department
  - Then the changes are saved

- Scenario: Update non-existent employee
  - Given a non-existent employee ID
  - When I PATCH details
  - Then the response is 404 Not Found

**Priority:** High  
**Story Points:** 3  
**Dependencies:** E01  
**Notes:** PATCH only updates provided fields.

---

### User Story 3: Soft Delete Employee
**User Story:** As an HR I want to soft-delete an employee So that historical data is preserved.

**Acceptance Criteria:**
- Scenario: Soft-delete employee
  - Given an active employee
  - When I DELETE the employee
  - Then the status is set to "INACTIVE" and not removed from DB

- Scenario: Fetching deleted employee
  - Given a soft-deleted employee
  - When I GET `/employees`
  - Then the employee is not returned unless filtered by status

**Priority:** High  
**Story Points:** 3  
**Dependencies:** E01  
**Notes:** Soft-deleted employees are excluded from active lists.

---

### User Story 4: Employee List Pagination & Filtering
**User Story:** As an HR I want to list employees with pagination and filtering So that I can efficiently manage large datasets.

**Acceptance Criteria:**
- Scenario: Paginated results
  - Given more than 50 employees
  - When I GET `/employees?page=2&size=20`
  - Then 20 employees are returned for page 2

- Scenario: Filter by department
  - Given employees in multiple departments
  - When I GET `/employees?department=Shipping`
  - Then only Shipping department employees are returned

**Priority:** High  
**Story Points:** 5  
**Dependencies:** E01  
**Notes:** OpenAPI docs must show filter options.

---

### User Story 5: Employee API Schema Documentation
**User Story:** As a developer I want OpenAPI schemas for employee APIs So that integration is clear and consistent.

**Acceptance Criteria:**
- Scenario: OpenAPI docs available
  - Given the application is running
  - When I access `/swagger-ui.html`
  - Then employee endpoints are documented with request/response examples

**Priority:** High  
**Story Points:** 2  
**Dependencies:** E01  
**Notes:** Examples must cover all fields.
